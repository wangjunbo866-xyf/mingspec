# Wide Refactoring

在一个共享接口、类型或名称的调整影响多个调用方、无法按普通业务切片交付时使用。机械操作不保证业务语义不变；对外契约或兼容承诺变化仍须回 SPEC 确认。

## Find the Impact

从改动对象及必须保持的行为出发，结合真实定义/引用、调用链、配置、数据边界和测试，映射到功能模块、规格及相关在途 Patch。文本搜索只是线索；动态调用、字符串配置和未检索来源需要说明检查方法与缺口。已有主规格中的业务规则没有变化时直接引用，不为了代码重命名强改规则 ID。

在主责模块的同一 Patch 记录受影响来源与读取基线、旧/新形式、不变项、排除影响依据及必要回归。依赖并行 Patch 时核对具体任务/版本，不因为位于不同目录就认为可并行。历史 Patch 保留原时点含义，不随新代码批量改写；调整其他在途任务须在相应授权内保留旧记录。跨模块或跨域的同一目标维护一份主责 Patch，不为每个命中项建新 Patch 或独立影响索引；只有能分别交付和验收的目标才拆分并记录真实依赖。

## Choose the Sequence

- **可控原子修改**：所有实际调用方可在一次受控修改内更新且编译/回归通过时，可以直接替换，不强造兼容层。
- **先兼容**：需要分批推进时，先引入新形式并保持旧调用可用，验证约定行为。
- **分批迁移**：按实际影响范围分组，每批依赖兼容任务；有共享变更或其他真正依赖时明确连接。每批交付自己的修改、所需测试和文档，通过适用检查后再标完成。
- **最后清理**：清理任务依赖所有必要迁移。核对当前调用方和相关在途工作不会重新引入旧调用，再移除旧形式；仅搜索不到旧名称不足以证明行为及集成正确。
- **集成例外**：无法让每批独立通过整体检查时，按项目已有授权隔离并集成，设置依赖全部必要批次的集成验证任务。批次如实记录局部结果及集成未验证；最终通过前不宣称整体通过。方法建议不自动授权建分支、合并或部署。

完成条件：选择的顺序有实际影响依据，清理依赖完整，局部与整体验证边界明确；未知调用方、基线或兼容问题仍阻塞相关清理/交付。

## Method Source

方法借鉴 Matt Pocock 的 to-tickets：纵向切片、阻塞关系、expand–contract 及集成例外。本产品采用自身任务引用与授权约定，直接维护同一 Patch 的 tasks.md；不依赖上游安装，也不生成逐票目录后再转换。实现时核对的上游原件、版本依据和适配范围留所属产品 Patch 的 Evidence；此处是来源说明，不是运行时调用。
