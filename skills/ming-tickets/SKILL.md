# Ming Tickets

版本：0.1.3。维护任务与规格的衔接；业务规则和验收预期由 SPEC 表达，实施、TDD 和独立审查由选定执行者按项目流程完成。可被显式调用或在已授权完整交付中接续，发现本 Skill 不等于取得写入授权。

## Identify the Work

1. 从当前请求和已有授权区分查询、起草任务、修订任务或核对结果。查询只读；讨论方案、回答澄清或只要求 SPEC 时不创建/改写 tasks。明确任务编排请求或完整交付授权覆盖本步时，先说明将写入的目标与产物，再继续；已有授权内不逐项重复审批。
2. 解析本 SKILL.md 的符号链接真实位置，以此读取相对资源。读取目标 AGENTS、根→域→模块规格导航、相关 Patch、SPEC 和现有 tasks；产品方法从安装位置读取，项目规则从目标读取。当前规格按 [Canonical Home](../ming-spec/references/spec-home.md#canonical-home) 使用域/模块/patches 布局；旧布局中的当前资料需按授权迁移，查询只读，目标异常缺失时报告具体缺口。
3. 核对实际工作区基线、未提交/并行内容及允许修改范围。默认维护主责模块内同一 Patch 的 tasks.md；跨模块或跨域仍引用同一主责 Patch 及各模块实际规则，不因涉及多个模块复制任务集。已有任务保持原任务 ID、记录与证据，版式可沿用。当前 Patch 不明确时先定位，不能凭猜测另建 Patch、逐票目录或第二份任务来源。

完成条件：目标、操作、授权、规格/任务位置与实际基线明确；未解缺口仅暂停依赖它的动作。

## Bind the Specification

从 [Ming Spec 修订现有 Patch](../ming-spec/SKILL.md#revise-an-existing-patch) 接续时，明确同步整个 Patch 的授权覆盖已有任务修订，按 Identify the Work 说明目标后继续。只改 SPEC 时仅报告任务影响，连待重核标记也不写；尚无任务时仍须有明确拆任务或覆盖创建的完整交付授权。

起草或修订前，读取实际 SPEC 的完整相关规则、场景、AC、范围与设计决定。新建任务采用 [任务模板](assets/tasks.md) 的 mingspec-tasks-v1 五字段，必须读取 [Run Task Checks](references/task-checks.md) 的格式、旧文件保全和调用步骤；修订现有任务时按同一资源核对兼容与转换权限。保留以下最小信息，不强制大表或重复共用段落：

- 任务 ID 与交付摘要：ID 在本 Patch 内唯一、稳定；跨 Patch 引用带真实任务位置。改标题、调顺序不重编号，删除/合并保留原身份与去向。
- 规格引用：来源地址、实际读取版本/可取回修订依据、规则 ID 与相关 AC ID；前置验证引用明确问题及判据。共用地址/基线可放文件开头，各任务仍能唯一解析自己的引用。
- 阻塞关系：以任务 ID 指明真正前置条件；五字段格式无依赖写 `blocked_by: []`，旧格式沿原版式明确无依赖。跨 Patch 指向具体任务和适用完成结果，不仅写模块名。
- 执行边界：引用 SPEC 的范围、禁止项和公共测试边界，补充本任务允许触及的部分与必要排除项；文件清单不扩大授权。
- 验证与状态：具体方法/命令或可观察交付，当前状态、真实结果和证据位置；未执行写待执行，不能填预计成功代替结果。

规则/AC ID 须结合来源路径定位；字段语法、受支持的 AC 表和旧格式处置执行上述 Run Task Checks。缺失、重复、冲突或歧义交回 [Ming Spec](../ming-spec/SKILL.md)，不发明规则、验收门槛或锚点；已明确的其他任务可继续。

任务保留摘要和执行信息；业务条件、例外、阈值、权限及验收预期引用 SPEC，不复制第二份规范。验证段写公开检查边界、方法及覆盖的 AC/场景。测试可含具体断言，实际结果和历史可保留当时数值，但不据此改业务规则；新决定先回同一 SPEC 再核对任务。现行规则、候选与历史按各自状态使用。

完成条件：每项所需规则/判据可唯一找到，任务与 SPEC 的含义一致；无法可靠绑定的任务明确未就绪。

## Decompose and Check Dependencies

普通功能按窄而完整的纵向交付拆分，贯穿该结果实际需要的实现层次；每项足以独立验证，并携带自身所需测试、文档和结果。不要仅按数据库、服务、界面分层排队，也不为没有该需要的任务强造层次或测试。

实施有准备依赖或关键技术假设未证实时，将所需准备与可行性验证列为同一 Patch 的前置任务；没有该类依赖不强制实验。先拆已明确的工作及有明确边界的验证任务，未知方案所依赖的实施保持待定，不编造未来实现来填满任务表。执行前写清问题/假设、环境/版本/输入、成功与失败判据、权限及数据影响，复用已有有效授权；规格维护授权不自动授予验证代码执行、服务操作、安装或数据写入。只暂停依赖尚未满足条件的实施，其他已获授权任务可继续。

将实际观察与证据引用回写 Patch 第二章，可行性结论及设计/测试决定回第四章，失败假设、未决项及阻塞回第五章；通过/失败/未运行与适用范围分别说明。技术验证判据与功能 AC 区分，验证通过不等于功能已交付或验收通过；实质变化同步受影响规则/AC 并重核授权范围。回写须符合 Bind the Specification 和 Hand Off and Reconcile Results 的职责与授权；只获准任务整理时，将需改 SPEC 的具体决定交回 Ming Spec，不越界代写。

原始日志、探测输出和临时脚本复用目标原任务/Issue/PR、已有证据或测试工具位置，Patch 引用这些来源；位置不明先查目标约定，不新建独立 `verification/` 或改名建立同等用途目录。已有材料按保护约定保留，此规则不自动授权迁移或删除。

共享接口、调用链或类型的大范围机械重构时，必须读取 [Wide Refactoring](references/wide-refactoring.md)，按实际影响选择原子修改或分批迁移；不同模块、文件或不同 Patch 本身都不证明独立。

核对全部任务 ID 和阻塞引用：缺失/歧义、自依赖、循环、引用已退役任务，以及对旧基线完成结果的误用。循环或未知依赖不视为可开始，记录缺口与受影响任务；仅在原规格/授权已明确时修正，不凭顺序猜依赖。选出依赖结果适用于当前基线、必要来源与授权明确的可开始任务，其他真正独立的任务可继续；暂时没有可开始任务时报告具体阻塞。

对照本次范围的规则/AC/前置问题核对任务覆盖；可以一对多、多对一，不强制一条规则一张工单。已交付复用、延期或无法拆分项写明来源及原因，不以任务数量代替覆盖。跨任务集成验证可以单列，不能接收前面任务欠下的局部测试或文档。

生成或更新 tasks.md 后，按 [Run Task Checks](references/task-checks.md) 实际执行检查、读取并记录结果，再交接；非零、未运行及旧格式缺口按该步骤处理。

完成条件：每项有可验证交付和必要局部工作，范围内要求有去向；依赖图可解释，可开始项不依赖未知或不适用结果，命令检查结果与未检查部分明确。

## Hand Off and Reconcile Results

交出任务时指向 tasks、实际 SPEC/基线、项目入口和已有证据，说明可开始项及真实阻塞。执行者先读取这些来源，再按已授权方式实施；任务生成本身不启动代码执行、安装、提交或部署。记录本次实际采用的执行 Skill/方法、版本或可取回来源及本地适配；不把借鉴 to-tickets 说成运行它，不推断任意第三方可直接接入。

交接中提供已解析的 tasks 检查命令、目标 Patch 和结果记录位置，并要求执行者每次状态回写后运行 [Run Task Checks](references/task-checks.md)；Ming Tickets 回写核对结果或修订任务后也运行。跨机器接手重新解析产品路径，不能只给待填占位命令。

执行者就近回写实际完成内容、候选基线、检查/结果、证据及未解决问题。Ming Tickets 核对遗漏与一致性；字段完整、链接有效或状态声明不能代替实际检查。五字段任务的 `state: completed` 表示本项交付和必要验证完成；旧格式沿原版式标记完成，不另加第二套状态。必要失败、未运行或依赖未满足时不能标完成，不适用说明理由。项目审查要求继续适用，本项完成不代替整个 Patch 验收、独立审查或主规格吸收。

规格、输入或实现基线实质变化后，读取新旧相关内容，按影响重核任务及其下游依赖。保留任务 ID、旧版本和原始证据，在同一任务注明当前待重核；原完成状态及其证据只适用于旧基线，不能释放当前依赖，旧格式的历史勾选同样如此。依据实际检查决定复用、补验、补做或退役并记录原因；未受影响的任务继续，措辞调整也需确认语义未变后才沿用结果。原件或结果不可取回时报告证据缺口，不猜测通过。

收尾由 [Ming Archive](../ming-archive/SKILL.md) 按验收、独立审查和已有授权吸收主规格；本 Skill 只报告本次任务产物、结果、引用有效性及阻塞，不把它们直接升级为已交付规则。

上述回写仅在任务维护授权内执行；未获授权时将具体任务 ID、影响和未同步原因留在答复或获准的 SPEC 记录，保持任务文件不变。任务或证据揭示新业务/设计决定时，按 Ming Spec 的修订流程交回同一 SPEC；当前只获准任务整理则报告规格缺口，不在 tasks 中决定业务规则，也不越界改 SPEC。

完成条件：下一位执行者能只凭交接来源定位规则、范围和当前可做事项；检查结果与证据适用性分明。无法接手时明确缺少什么，不以“已生成 tasks”宣称交付完成。
