# Patch Workflow

本页处理目标定位、候选写作与修订；授权和资料保护沿 [Shared Boundaries](shared-boundaries.md)。

## Choose the Change Tier

先按实际业务模块影响和风险选档，在原请求答复、Patch 或现有记录中用一句话说明档位与理由；不新增分档表单。文件数量和改动行数不决定档位，同一模块的规格、测试与说明同步不自动算跨模块。

| 档位 | 适用条件 | 必需流程 |
| --- | --- | --- |
| 小修 | 已有主规格；单模块、局部低风险且可直接验证的修正，例如纠正错字/链接、澄清不变语义、恢复已确认规则；不引入新能力或改变既有业务承诺/AC | 直接修正主规格，保留稳定 ID、条件与例外，做适用检查，就近留一行来源；默认不建 Patch、AC、tasks，也不要求独立审查 |
| 标准变更 | 单模块行为变化或新增能力，且没有完整档风险 | Patch + 稳定 AC + 适用验证 + 一次独立审查；五章可简写，任务按实际协作需要或明确请求创建，结果可直接留 Patch |
| 完整流程 | 跨业务模块；或单模块存在破坏兼容、权限/敏感数据边界、不可逆数据迁移、重要可用性影响等高风险 | Patch 与 AC、逐模块影响/旧场景对账、按真实依赖组织任务、适用的前置验证/局部与集成验收、独立审查、主规格及地图收尾；无对应需要不造空产物 |

小修一行来源可写：`来源：2026-11-13 用户请求/Issue/提交——修正点；检查：实际结果。` 使用真实已知来源，没有 Issue 或提交可写日期与请求摘要，不为留痕创建提交或额外文件。实际检查细节可在原对话/任务中报告。涉及实现的小修仍须验证修复，不能把尚未交付的新承诺写成当前行为。

无法确认小修条件时至少采用标准档；发现跨模块或高风险时升级到完整档，保留已做修改和证据，在同一目标补齐受影响步骤，不倒造此前已执行。跨模块以规则/能力的真实影响判断，不仅看改了几个目录。既有资料异常缺失、并行冲突、只读或仅改 SPEC 的权限不因分档放宽。首次补录既有能力沿 First Specification，不强造功能 Patch；其验证与审查按实际范围采用标准或完整档。

收尾按 [Independent Reading Check](spec-home.md#independent-reading-check)默认把独立阅读与最终差异核对合为一次审查、一份记录，完整档也不自动增加第二轮。只有明确用户/项目要求或具体风险需要额外检查时才说明理由增加；分档本身不要求再次审批。

## Confirm the Target

核对明确项目根、本次范围、主规格位置或从未建立的依据、已有 HEAD、实际读取版本及未提交正文。HEAD 不能替代工作文件。不为补基线建立初始提交。沿目标 AGENTS、README、规格地图和原任务定位检查命令、收尾方式、域/模块职责及任务/证据，不按项目名单或安装示例猜测。

需要 Patch 的标准/完整档只处理一个主责 Patch；小修直接按上节维护主规格；独立新目标保留原 Patch，按有效授权另起候选，未授权则只建议。主规格或地图异常缺失/删除/冲突、基线不明或混入另一个 change 时，保留现场和已读来源，只暂停依赖步骤，不借安装副本或自动恢复文件。首次未建与异常缺失按 [First Specification](business-map.md#first-specification)区分；旧布局按 [Migration](spec-home.md#migrate-an-existing-project)处理，只读可沿旧来源回答。

## Draft Content

标准/完整档候选使用[五章模板](../assets/spec.md)：目标范围、现状依据与影响、行为及验收、必要设计与测试决定、未决项与来源。区分已确认契约、静态观察、真实运行和拟改变行为；说明旧/新行为、不变项、理由、调用/接口/文件职责和排除影响依据。小修走 Choose the Change Tier，不进入候选模板。

每条规则围绕一个可独立验证的行为，使用稳定 AC 关联结果。不同独立行为分别描述，共同条件可明确引用，场景保留例外和边界。既有长规则不因提醒自动拆改；无通用字符上限，未授权正文保持。修改后保留稳定地址与旧场景映射。

准备实施前，确认正常、异常、边界及兼容预期、公共测试边界和必要决定足以判断；未知列为具体阻塞。标题齐全或预期结果不是实际验证。主规格使用 [Main Specification](spec-home.md#independently-readable-main-specifications) 的阅读结构，不能直接搬候选五章。

## Revision Scope

定位同一 Patch、实际修订基线和允许写入职责。只改 SPEC：读取 tasks 判断影响，但仅写获准候选；在允许输出报告受影响任务 ID 和缺口，tasks、旧回执及待重核字段保持不变。

明确同步整个 Patch 的已有规格/任务，或完整交付已覆盖时：说明写入目标，接续 Ming Tickets 修订受影响任务，不逐个重新确认。区分 tasks 从未建立与异常缺失；仅修订材料不补造文件，明确编排/完整交付才可新建任务，异常缺失 SPEC 仍不可自动重建。

## Reconcile a Revision

从变化来源双向核对规则/AC、设计、任务引用/依赖、证据适用性和当前导航，不以读取顺序限制影响方向。任务或技术证据暴露不一致时，保留原始观察并将新决定交回同一 SPEC；未确认的业务取舍保持未决，技术失败不自动授权放宽业务规则。

规则含义变化时按 [Reconcile Results](../../ming-tickets/references/task-workflow.md#reconcile-results)核对旧 ID、版本、证据及真实下游；获准写 tasks 才交 Ming Tickets 标待重核，否则只在允许输出说明。无关结果保留，未运行的检查不能报通过。

完成时报告实际修改、核对/保持项、未同步项及原因、受影响任务/证据、剩余缺口和下一步。材料一致或只读请求允许零写入，不为留痕制造修订。候选修订完成不证明实现、业务验收或吸收完成。

## Name the Candidate

新候选放主责模块 `patches/<patch-id>/spec.md`，同一职责只保留一份权威正文。原始需求、任务、证据可各有独立职责；旧兼容增量只作历史，不是新候选必需产物。文件名不改变交付状态。

纯回执/历史保留适合其职责的原名（例如 change.md），不因结构或目录名变成新候选；已吸收历史不自动改名或重开。未授权改名的既有正文及引用保持。获准改名时先保全实际原件及并行内容，再同步当前导航、回链、跨模块锚点和活动检查路径；保留规则 ID、AC、版本、语义及原始日志，不称重新验收。

同 Patch 的已交付切片与未交付候选可共存，分别标注范围，继续由 spec.md 承载候选职责。不能因局部交付标整个 Patch absorbed，已交付主规格保持完整。
