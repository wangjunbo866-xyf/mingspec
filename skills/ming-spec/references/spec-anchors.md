# Stable Rule Anchors

在起草/修订 Patch、补旧规则定位或收尾模块主规格时执行本流程。锚点标识规则，AC ID 标识验收条件；一个规则可有多个 AC，一次 Patch 可影响多个模块的规则。每条规则以其所属模块的唯一主规格为准，跨模块引用真实地址，不复制另一份当前规则。

## Locate the Rule

1. 从目标导航读取主规格、已确认版本与相关在途 change，记录实际读取的修订及未提交正文依据；首次新功能确认尚无主规格时，记录该事实与计划地址，在 Patch 内起草，不预建主规格。旧正文异常缺失继续报告缺口；只读请求不写。
2. 对每条可独立改变的规则，优先复用显式 HTML `id`/`name`。新 ID 使用小写 ASCII 字母/数字与连字符，例如 `rule-display-name`；在同一文件内对显式和标题生成的锚点查重。同名 ID 在不同主规格中可以存在，引用须包含主规格路径。
3. 原规则只有标题链接时，先凭正文和来源确认唯一目标；在已授权维护范围内补显式锚点，保留原正文和旧标题链接。改标题时保留原 ID，必要时留旧标题链接的兼容锚点；兼容 ID 同样查重。缺失/重复/歧义未解时保留现场，暂停相关写入，不从相似名字猜目标。

模块主规格使用 [主规格模板](../assets/main-spec.md)，按 [独立阅读约定](spec-home.md#independently-readable-main-specifications)补齐本次内容；首版为 `current-v1`，已有独立模块版本按真实修订接续；迁入已有规则时注明旧版本、规则映射与原件依据，版本格式和职责见 [Canonical Home](spec-home.md#canonical-home)。规则块最小写法如下；这是定位示例，不是完整规则模板，具体业务规则与 AC 从目标读取：

```markdown
<a id="rule-display-name"></a>
### Display Name

当用户触发操作时，展示模块应按已确认顺序选择显示名称。

说明：在对应规则或场景保留完整条件、例外与可观察结果。

来源：填写实际已吸收 Patch 或经确认的既有行为基线的相对链接及版本。
```

规则块含该标题的正文和下级场景；同级或更高标题开始另一块。场景按实际行为表达，不要求 OpenSpec 的 Requirement/Scenario 标记、MUST 或增量语法；迁移旧格式时逐项保全条件与例外，不机械删词。由模型按语义核对范围，锚点不是机械文本替换指令。无需给背景介绍等所有标题加 ID；新增 ID 不随章节编号、措辞或位置改变。

完成条件：每条已有目标可唯一定位，新增目标明确为计划 ID，必要旧入口仍可用；未解定位缺口及只读边界清楚。

## Describe the Change

规则变更在 [五章模板](../assets/spec.md) 第二章填写受影响锚点清单，写全主规格路径、读取版本/工作区依据、操作、旧/新规则及不变条件、AC。完整新规则可放第三章并从清单引用，不在多处复制正文；受影响规则的条件与场景须可独立理解。基线以真实读取为准，HEAD 不能代表未提交编辑。

仅补锚点、修链接或核对既有吸收关系时，直接维护原规格与 Patch；目标清单、基线和检查结果留原任务的既有记录，不为套五章模板新建 SPEC、维护目录或独立索引。

- **新增**：先核对无重复能力及 ID。主规格尚无该规则时写计划地址并标“新增，尚不存在”，不用虚假的可点击链接；收敛后改成真实目标。首次能力候选也保留拟议/交付状态区别。
- **修改或复用**：链接现有规则，说明旧行为、完整目标与保留项；只恢复已确认行为的小修沿项目记录引用该锚点，不为了清单新造 Patch。
- **场景对账**：读取完整旧正文，在同一目标清单或验收说明中逐项记录旧场景是保留、修改、退役，还是映射到拆分/合并后的规则和场景，并关联 AC；新增场景另列。比较触发条件、结果、例外和边界，不用同名或数量相同代替语义核对。场景改名仍须追到原项，有意删改写决定来源、原因、替代/无替代与 AC 影响；实质变化按授权约定处理，未解遗漏只阻止相关交付与吸收，不强制新表或文件。
- **删除或替代**：记录旧规则、退役原因、替代/无替代及来源。旧 ID 留简短退役入口或可追溯迁移映射，旧正文由原 change/可取回历史保留；旧 ID 不交给无关新规则。删除规则的语义与修复链接分别核对。
- **纯重命名**：规则身份与行为不变时保留稳定 ID、必要旧入口及新旧名称对应；若同时改行为，变化部分按修改列出，不能用改名绕过 AC 和授权核对。
- **跨规则或并行影响**：逐一列每份主规格的目标；同 ID 重叠和共享接口/条件均需比较，不从不同 ID 推断兼容。

完成条件：清单与行为/AC 一一可追，已存在、计划新增和退役目标可区分；路径、锚点、工作区依据及授权没有待猜内容。

## EARS Requirements

起草或修订规范性需求、约束及验收预期时使用 EARS；判断依据是条款职责，不是所在章节。中文采用下表的对应句式，原英文术语、代码标识及目标文档结构保留。背景、职责归属、实施范围、理由、历史引文、设计步骤和实际验证记录不强套 EARS，也不伪造为系统自动执行的功能。

| 适用情况 | 中文句式 |
| --- | --- |
| 始终成立的要求（Ubiquitous） | `〈系统主体〉应〈可观察响应或约束〉。` |
| 事件触发（When） | `当〈事件〉时，〈系统主体〉应〈响应〉。` |
| 状态持续（While） | `在〈状态持续成立〉期间，〈系统主体〉应〈响应〉。` |
| 异常输入或不期望情况（If / Then） | `如果〈异常条件〉，那么〈系统主体〉应〈响应〉。` |
| 产品包含可选能力（Where） | `对于具备〈可选能力〉的产品，〈系统主体〉应〈响应〉。` |
| 组合条件 | `在〈状态〉期间，当〈事件〉时，〈系统主体〉应〈响应〉。`；异常分支可用 `如果……那么……` |

本项目写作约定：`应` 表示必需响应（shall），`不得` 表示禁止响应。原规则中的 `可/允许` 保持原许可强度；必要时写为“系统应允许……”，不能把“可执行”改成“必须执行”。Where 表示能力适用条件，不等于把强制要求改成可选。无触发条件的要求使用始终成立句式，不为所有句子虚造“当”。上述中文是项目表达约定，不是官方中文标准；模式及次序来源见 [EARS 作者说明](https://alistairmavin.com/ears/)。

改写时先识别主体、状态/触发、响应、范围与例外，再选句式。不同触发或独立行为分句，保留共同条件的作用范围；一个响应可以包含不可分割的多个结果，不机械按“和/并且”拆开。系统主体沿用目标已有职责名，不因改写新增部署服务。来源和证据另作说明，仍有规范约束的句子不能借“说明”标签逃避核对。

AC 表格保持原 ID 和输入/条件/验证方式；验收预期列写完整 EARS 句子，必要条件在句中重述，使离开相邻行也能明确判断。同一 AC 含多个分支时，在原 ID 下分别写句子并保留已有子检查编号；没有业务变更授权时不新增验收门槛、重编号或抹去例外。实际结果与预期分开，句式改写不改变未执行/已通过状态。

## EARS Completion Check

交付前逐条读取本次规范性条款及每个 AC 的预期，并与实际旧正文对照，在原任务记录以下结果：

1. 每条要求有可识别的系统主体、适用模式和明确响应；需要的状态、触发及异常条件完整，始终成立的要求没有虚构触发。
2. 正常、异常及可选分支分别可判定；原许可/禁止强度、否定、数量、时间、顺序、范围、例外及外部引用保持，未把技术未知写成已确认规则。
3. 每个旧规则锚点、AC ID 和已有子检查仍映射到原行为；纯改写可保持原 ID 下多句，不用 ID 数量相同代替语义保全。
4. 范围、来源、历史及验证记录各保留职责；未适用 EARS 的条目说明类别，不能把真正系统要求归入背景而漏改。
5. 检查结果区分“EARS 句式已检查”“语义已对账”“链接/格式通过”和“功能验收通过”。必要遗漏未解时不声明 EARS 整体完成；检查器或关键词匹配仅作辅助，独立审查继续按目标约定执行。

完成条件：本次全部适用条款和 AC 预期已核对，非规范材料分类有据，稳定标识与完整语义保持，真实结果留原任务。此检查属于既有交付核对，不增加 PLAN、自动校验器或新的审批阶段，也不授权批量改写范围外规格。

## Verify Removed or Renamed Behavior

验收规则删除或纯规格改名时，先从当前主规格读取旧行为正文、条件与场景；已被同步移除时，从原 Patch 或可取回历史恢复阅读依据。只有标题或无法说明行为的文字不是可用基线；仍缺依据时记未验证、说明缺口，只暂停依赖验收，不从空输出推断不存在。

- **删除**：对照旧行为追查实际调用与共享路径，并执行适用验收证明行为退出。仅关键词搜索无结果不够；仍能提供旧行为的路径须处置，迁移用途或无关保留行为不能误判为残留。必要验证未运行或证据不足时保持未验证。
- **纯改名**：核对旧行为与条件仍成立、稳定 ID 与必要旧入口保留；文档标题不要求代码符号或文件强改。伴随行为变化的部分按修改验收，缺证据不记通过。

完成条件：每项有可用基线、对应操作的实际结果和来源，或明确的未验证原因与阻塞范围；不会因搜索不到旧标题把删除判成功，也不会把纯改名误判为功能缺失。

## Consolidate and Check

1. 交付收尾须已有按 [Check the Evidence](../../ming-archive/SKILL.md#check-the-evidence) 核对本次候选与范围的结果；缺失先执行该节，已有结果仍适用时复用，范围或基线变化按影响重核。写前重读每个目标和相关 change，与清单的读取基线比较；并行新决定原样保留，冲突只阻塞相关项。保留比较结果，不能覆盖后再解释。
2. 按清单逐项写入已验收交付的完整规则和场景；首次交付时创建主规格，已有则更新。保留 ID、条件/例外、未改条款及并行内容；新增 ID 查重，退役按上节保留追溯。主规格明确已覆盖范围与缺口，能独立表达纳入的当前规则，读者无需拼接 Patch。
3. 在受影响规则末尾或 Sources 链接实际来源 Patch 或经确认的既有行为基线，并使每条规则的来源可定位；在第五章记录各模块实际吸收版本、地址与结果/未完项，再同步对应层地图/导航。每项有效条款及独立结论均交代去向：已吸收、仍在 Patch 的候选、保留为历史依据，或有决定和理由的不采纳；给出实际位置/引用，不逐句登记背景。工具忽略的有效内容也须可取回，原始证据留原任务，不为此新增目录、文档类型或阶段，去向核对不授权删除。部分吸收保持其余项待完成，全部拟交付项已核对后才标整个 Patch 已吸收；模块主规格版本独立，不因其他模块、Skill 或产品包版本变化而同步升级，纯迁移不表示业务重新验收。
4. 逐项检查：地址唯一且可达、正文完整、基线差异已处理、未变约束保全、来源双向可追、状态与版本有依据，并重读当前导航。已一致时保持零差异，不反复追加相同来源或重写历史。

完成条件：清单每项都有真实结果，当前正文/来源/地图一致，必要失败和未完成项没有被吸收状态掩盖。链接检查只证明可达，语义保全须读取正文核对。交付收尾（含单独调用本节）仍须在规则、地图及必要知识写入完成后执行 [Final Review](../../ming-archive/SKILL.md#review-the-final-difference)，本节核对不能替代其必要检查、独立复核及结果记录；只接续该章节，不重启整个流程。收尾不等于自动合并、提交或部署。
